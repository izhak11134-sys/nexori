# עריכה בתוך NEXORI עם Firebase — הכנה וחיבור

האתר עדיין אינו פורסם. הקוד כולל כניסה ב־`/admin`, עריכת כרטיסיות במקום, טיוטה משותפת למנהל, החלת תוכן ושחזור גרסאות. אין עדיין פרויקט Firebase אמיתי מחובר. קובצי HTML להורדה נשארים תצוגות עצמאיות; מערכת הניהול החדשה מיועדת לאפליקציה שפועלת דרך שרת HTTP/HTTPS, ולא לקובץ שנפתח מתיקיית Downloads. אין צורך להוריד HTML אחרי כל עריכה.

## מתחילים רק מחשבון Google

1. פתח https://console.firebase.google.com/ והתחבר לחשבון Google שבבעלותך. אם אין לך חשבון Google, בחר יצירת חשבון ב־https://accounts.google.com/signup. אם הכתובת `nexoriofficialon@gmail.com` היא חשבון Gmail שלך, אפשר להשתמש בה. אין שם משתמש Firebase נפרד.
2. אין צורך לשלוח לי סיסמה, קוד אימות, קובץ service account, מפתח פרטי או פרטי כרטיס אשראי.
3. לאחר שהצלחת להיכנס, אפשר להמשיך יחד ליצירת הפרויקט. שמות ומיקומי כפתורים בקונסול יכולים להשתנות; ההדרכה הזאת היא רצף הפעולות הדרוש ולא תיעוד של ממשק שנבדק בזמן אמת.

## יצירת סביבת פיתוח לפני השקת האתר

1. צור פרויקט חדש, למשל `NEXORI Development`. לא נשתמש בהגדרות Firebase מתוך קובצי ה־HTML הישנים שהעלית. Google Analytics אינו נדרש למערכת העריכה הזאת.
2. עבור פעולות השרת ואחסון התמונות בתצורה הזאת נדרשת תוכנית Blaze וחשבון חיוב. עצם הבנייה המקומית אינה מפעילה חיוב. לפני קישור אמצעי תשלום נבדוק יחד את התנאים והעלויות העדכניות של https://firebase.google.com/pricing ושל Cloud Storage/Cloud Functions. קיימות מכסות ללא חיוב, אך אין הבטחה שהשימוש יהיה חינם. הגדר התראות תקציב; התראה אינה תקרה ואינה עוצרת חיוב. בקוד הוגדרו `maxInstances: 3` ואין שרתים שחייבים להישאר פעילים, אך זה אינו מגביל את כל עלויות Firebase.
3. הוסף Web app לפרויקט. העתק את הגדרות אפליקציית האינטרנט ל־`.env.local` לפי `.env.example`. הגדרות web כגון `apiKey` ו־`projectId` הן מזהים ציבוריים; האבטחה נשענת על Auth, כללי הגישה ופעולות השרת. אין להכניס service-account או סודות ל־`VITE_*` או ל־GitHub.
4. הפעל Authentication עם ספק Email/Password בלבד. הוסף חשבון מנהל מהקונסול באמצעות הדוא״ל הרצוי וסיסמה חזקה שאתה בוחר. אתר זה אינו מציג הרשמה לציבור ואינו מעניק הרשאת מנהל בעקבות הרשמה.
5. **בחירת מיקום המסד מושהית עד שנחליט על השוק הראשוני.** ראה [בדיקת המיקום מול הקהל](firebase-region-decision-he.md). צור Cloud Firestore במצב production רק לאחר החלטה. אי אפשר לשנות את מיקום אותו מסד אחרי יצירתו. `europe-west1` היא ברירת המחדל הטכנית בקוד ואינה מסקנת מחקר על קוני אנימה; אם נבחר ארה״ב נעדכן את אזור פעולות השרת ואת הלקוח לפני פריסה.
6. צור Cloud Storage ובדוק את המיקום והחיוב. העתק את שם ה־bucket בפועל, כולל הסיומת, אל `VITE_FIREBASE_STORAGE_BUCKET`. אין להניח שהסיומת היא תמיד `appspot.com`; פרויקטים חדשים יכולים להשתמש ב־`firebasestorage.app`.
7. לאחר יצירת משתמש Auth, העתק את UID שלו. ב־Firestore צור מסמך באוסף `admins` עם מזהה מסמך **ה־UID הזה**, ושדה Boolean בשם `active` שערכו `true`. לא משתמשים בדוא״ל כמזהה המסמך. המסמך נוצר ידנית על ידי בעל הפרויקט; אין הרשאה ליצור אותו דרך האתר.
8. הוסף את כתובת סביבת הפיתוח לרשימת Authorized domains של Auth לפי הצורך. התחבר במסך הניהול, שלח הודעת אימות אם מתבקשת, אמת את הדוא״ל, ואז התנתק והתחבר שוב. גם משתמש שמופיע ב־`admins` חייב להיות עם דוא״ל מאומת.
9. נגדיר CORS ל־Storage עבור כתובות הפיתוח המאושרות, כדי שאפשר יהיה לטעון תמונות פרטיות לתצוגת העריכה עם `getBlob`. `docs/firebase-storage-cors.example.json` הוא דוגמה בלבד; מחליפים את הדומיין בכתובת האמיתית. מנהל הפרויקט מיישם באמצעות כלי Google Cloud מורשים, למשל `gcloud storage buckets update gs://YOUR_BUCKET --cors-file=docs/firebase-storage-cors.example.json`. CORS אינו מעניק הרשאות גישה לקבצים ואינו מחליף Storage Rules.

## התקנת התשתית בפרויקט הנכון — בלי לפרסם אתר

פעולות אלה יבוצעו רק אחרי שניצור יחד פרויקט ונבחר את הגדרותיו. התקנת CLI והפעלת Emulator אינן התחברות לפרויקט אמיתי. ה־CLI במחשב המפעיל דורש Node.js נתמך, ו־Functions מוגדרות ל־Node.js 22.

```sh
npm ci
npm ci --prefix functions
npm run firebase:sync
npx firebase login
```

אין צורך לשלוח את פרטי ההתחברות בצ׳אט. לפני כל פריסה יש לבדוק את מזהה הפרויקט שנבחר, את כללי הגישה ואת החיוב. בפרויקט development ניתן לפרוס רק את תשתית הנתונים:

```sh
npx firebase deploy --project YOUR_PROJECT_ID --only firestore:rules,storage,functions
```

פקודה זו משנה שירותים בענן; היא אינה מפרסמת את Firebase Hosting. ה־CLI עשוי לבקש להעניק ל־Storage גישה הדרושה לבדיקה מול Firestore; יש לבדוק ולאשר בפרויקט הנכון. אין להחליף את הכללים בכללי `allow read, write: if true`.

אחרי הפריסה יש לבצע בדיקות אמיתיות של התחברות, אימות דוא״ל, הרשאות, CORS, תמונות, פעולות השרת ותקציב. בדיקת emulator אינה מוכיחה שהרשאות IAM או CORS בפרויקט אמיתי מוגדרות נכון.

```sh
npm run dev
```

האתר פועל בסביבת פיתוח. השקת Hosting אינה חלק מהשלב הזה ותבוצע בנפרד כשתחליט שהאתר מוכן.

## השימוש היומיומי שלך

- היכנס ל־`/admin` באתר והתחבר. קישור **Owner sign-in** נמצא בתחתית האתר. רק המנהל המאומת יקבל כפתורי עריכה וסרגל כלים.
- עבור לכל כרטיסייה ולחץ **עריכה**. גם One Piece, Naruto, Demon Slayer, Jujutsu Kaisen, Dragon Ball ו־Attack on Titan נתמכים. כותרת ורקע הכרטיסייה וכותרת ורקע העמוד הפנימי הם שדות עצמאיים. מוצרים, קטגוריות, תתי־סוגים, כרטיסי מדריכים, כרטיסי הבית והמידע נתמכים גם הם.
- **שמירת טיוטה** שומרת ב־Firestore ותמונות חדשות ב־Storage פרטי. השמירה דורשת חיבור; הודעת שגיאה אינה שמירה מוצלחת. מסך העריכה נשאר פתוח אם הפעולה נכשלה.
- **תצוגת הטיוטה** מסתירה את כפתורי העריכה ומציגה את העבודה שלך. זה אינו משנה מה המבקרים רואים.
- **החלת השינויים באתר** מחילה רק את הטיוטה שכבר שמרת. תמונות מקבלות גרסה מוכנה לפרסום, והשינויים נכנסים יחד לגרסה חדשה. בפרויקט שלא פורסם עדיין, הפעולה אינה משיקה את האתר לציבור.
- בחר גרסה קודמת ולחץ **שחזור גרסה** כדי להחזיר תוכן קודם למבקרים. נשמרת גרסה חדשה של השחזור. הטיוטה הפרטית נשארת ללא שינוי. **טעינת הגרסה המוצגת** מחליפה את הטיוטה ומחייבת אישור.
- אם שני מכשירים משנים תוכן, שמירה על גרסה ישנה תידחה. הורד גיבוי של העבודה הנוכחית לפני רענון; הגיבוי אינו שומר בשרת מעצמו.
- התנתק בסיום, במיוחד במחשב משותף. הסשן משתמש בשמירה למשך פעילות הדפדפן; לחיצה על התנתקות היא הדרך הברורה לסיים אותו. אין שמירת טיוטות מנהל ב־localStorage במצב הענן.

## גבולות המערכת והמשך העבודה

השינוי מנהל את הכרטיסיות והאזורים הקיימים. הוא אינו עורך עשיר לכל משפט באתר, אינו מאפשר עדיין יצירת רשומות מוצר חדשות, אינו בודק רישוי תמונות או אמינות ספק ואינו מפעיל קישורי שותפים. שדות קישור לחנות והערות מוצר הם הכנה פרטית ומוסרים מהגרסה הציבורית. נבנה את הכנסת המוצרים האמיתיים בהמשך התהליך שכבר סיכמנו.

טיוטה היא מסמך תוכן אחד מוגבל ל־600KB ללא קובצי תמונה; שמירתה משתמשת בבדיקת גרסה למניעת דריסה. כל תמונה מוגבלת ל־2MB ול־PNG/JPEG/WebP. בעת החלה השרת מפענח, מקטין את הגרסה המוצגת לעד 2400×2400 וממיר ל־WebP, מסיר מטא־נתונים ומסרב לקובץ שאינו תמונה תקינה. תמונות מקוריות שהעלית צריכות להיות מותרות לשימוש.

היסטוריה וקובצי תמונות אינם נמחקים אוטומטית: צריך לקבוע מדיניות שמירה וניקוי לפני השקה. קבצים שנוצרו בעת פעולה שנכשלה אינם נגישים לציבור בלי סימון שחרור ב־Firestore, אך הם יכולים לצרוך אחסון. תמונה שכבר פורסמה יכולה להישמר במטמון אצל מבקרים; שחזור אינו מבטל עותקים שכבר הורדו. אין התחייבות למחיקת קובץ ציבורי רק מפני שכרטיסייה שונתה.

Auth ו־Firestore/Storage Rules מגינים על הפעולות; שירותי Google מחייבים גם הגדרות פרויקט תקינות. לפני השקה נבדוק App Check, ניטור, תהליך שחזור סיסמה והרשאת מנהל, גיבוי/מחזור חיי הקבצים, מגבלות חיוב, פרטיות והעברת נתונים. App Check עדיין לא מופעל בקוד ואינו תחליף להרשאות.

## בדיקות מקומיות למפתחים — ללא חשבון Firebase

עם Java 21+:

```sh
npm run test:catalog
npm run test:content
npm run test:firebase-validation
FIREBASE_EMULATORS_PATH=/tmp/nexori-firebase-emulators npm run test:firebase
```

האמולטורים משתמשים ב־`demo-nexori`; אין לפרוס מזהה demo לפרויקט אמיתי. הורדת האמולטורים הרשמיים דורשת גישה ל־`storage.googleapis.com`. אם ההורדה חסומה, בדיקות השרת **לא הושלמו**; אין לדלג עליהן ולתאר את ההרשאות כמאומתות.

לפיתוח אינטראקטיבי אפשר ליצור `.env.local` עם:

```dotenv
VITE_FIREBASE_API_KEY=demo-key
VITE_FIREBASE_AUTH_DOMAIN=demo-nexori.firebaseapp.com
VITE_FIREBASE_PROJECT_ID=demo-nexori
VITE_FIREBASE_STORAGE_BUCKET=demo-nexori.appspot.com
VITE_FIREBASE_APP_ID=demo-app
VITE_FIREBASE_USE_EMULATORS=true
```

הפעל `npm run firebase:emulators` עם `FIREBASE_EMULATORS_PATH` תקין, ובחלון נוסף `npm run dev`. יש ליצור משתמש והרשאת UID דרך אמולטור או בדיקות בלבד, לא דרך נתונים של פרויקט אמיתי. `VITE_FIREBASE_USE_EMULATORS=true` מותר רק על localhost; הקוד מסרב לחבר אמולטורים כאשר העמוד נמצא בדומיין מרוחק.
